TWX Code Analyzer - user guide

The web application edition: everything of the analyzer plus accounts, workspaces, policies, quality gates, queued analyses, Process Center import, notifications and an API for pipelines. Sections marked admin need an administrator.

Overview

TWX Code Analyzer reads an IBM BPM / Business Automation Workflow export (.twx) and runs more than 150 static-analysis rules over its services, processes, coach views, business objects, scripts, toolkits and configuration. The result is a ranked list of findings with the exact artifact path, the offending line, the reason and the remediation, plus diagrams, artifact browsing, toolkit usage, search, exports and comparisons between snapshots.

The typical flow: Analyze an export (upload or Process Center import) → open the report (findings, overview, remediation) → accept what is not a real problem → fix the rest → analyze the next snapshot and compare. Teams formalise this with a rule policy and a quality gate that gives every analysis a pass / fail verdict, usable from a pipeline through the API.

Accounts and sign-in

Depending on how the server is configured you are identified by the company single sign-on (the container's security or a trusted header set by the reverse proxy), by a built-in account (sign up with an e-mail address and a password) or not at all (anonymous demo workspace).

  • Sign up / Sign in (top right) create and open a built-in account. Signed-in users keep their analyses, rule settings and accepted findings across sessions, browsers and devices, until they delete them.
  • Account (user menu) shows your profile, changes the password, manages personal access tokens for scripts and pipelines, and offers Purge all my analyses and Delete my account (removes everything: analyses, settings, accepted findings, tokens and the account).
  • Anonymous demo: without an account the browser gets a private, temporary workspace (a cookie); it is purged after the retention period of the server. Rule settings are read-only there.
  • Administrators are designated by the server operator in a properties file; they see the Administration page.
Sign-in security: passwords are stored as salted PBKDF2 hashes, sessions are HttpOnly cookies valid for 30 days, ten failed logins lock the account for 15 minutes.

Workspaces and teams

Everything you see (history, dashboard, settings, accepted findings) belongs to the current workspace, shown in the workspace menu at the top right.

  • Personal: your own analyses; only you see them.
  • Team: a shared workspace created by an administrator. Members see the same analyses, the same policy and the same accepted findings, so a team can run one baseline for its application. Team admins (named in the team) manage the team's policy, gates, notifications and accepted findings; other members can analyze, export and delete.

Switch between workspaces in the menu; the choice is remembered in the browser (cookie tca_scope). API clients select a team with the header X-TCA-Workspace: team:<id>.

Dashboard

The landing page of a workspace: totals (applications, analyses, average health, gate failures, storage), one row per application with its latest snapshot, health, change since the previous analysis, open findings, gate verdict and a health trend line over all its analyses, the applications that need attention (lowest health), the most frequent rules across the latest analyses and the recent analyses. Click a row to open the latest report.

Analyzing an export

  1. Export the process application from Process Center (or use the Process Center page to let the server do it).
  2. Analyze: drop the .twx file. Also analyze the bundled toolkits includes the non-system toolkits of the export in the rules (system toolkits such as System Data or the UI Toolkit are never analyzed).
  3. The analysis is queued: the server runs a fixed number of analyses at a time (workers) and shows the queue position, then the progress (rule n of m). Large exports take up to a few minutes. You can leave the page; the Queue entry of the user menu lists your jobs, and the History shows the report when it is done.
A workspace may have a storage quota; when it is exceeded the upload is refused with "quota exceeded" and older analyses must be deleted first. On some servers the uploaded file is discarded after the analysis (server policy): the report stays, but artifact browsing, diagrams and search are then not available for it.

Reading a report

The header shows the application, snapshot, file, product version of the export, the health score (100 = no open findings; it decays with the weighted score relative to the size of the application), the gate verdict and the policy the report was analysed with, the Executive PDF (one-page management summary) and Delete (permanent). Notes below the header report loader diagnostics and analysis coverage (scripts skipped because of syntax errors).

Tabs: Findings, Overview (counts, charts, inventory, top rules, toolkits), Objects & Diagrams, Toolkit Usage, TWX Search, Remediation.

Findings

Every finding has a severity (Critical, Major, Minor, Info), a score = severity weight × rule impact (the ranking key), the rule, the artifact path (application / type / artifact / step or script), the message, the evidence with the line and the source snippet, and the remediation. Findings marked review come from heuristic rules and need a confirmation in context.

Filter by severity, category, rule, artifact type, confidence and free text; sort by rank, artifact or rule; export CSV, HTML or PDF of the current selection. Click a finding for the detail: why it matters, what to do, Show in diagram (opens the artifact with the step highlighted) and, for workspace managers, Accept finding.

Accepted findings (baseline)

Not every finding is a defect to fix now: false positives, known technical debt, risks accepted by the owner. Accept finding (in the finding detail) records a reason with your name and date. Accepted findings:

  • stay in the report, marked accepted, hidden by default (show accepted in the filter bar);
  • do not count in the open findings, the weighted score, the health score, the verdict, the dashboard or the executive summary;
  • apply to every report of the workspace, past and future, as long as the same finding exists (same rule, artifact, step and location): after a fix the finding disappears by itself, and a new snapshot keeps the baseline;
  • can be reopened at any time (Reopen finding). The Compare page can hide accepted findings so only real regressions show.

Accepting requires the manage right on the workspace (owner of a personal workspace, team admin, administrator). Every acceptance is in the audit trail.

Remediation

The Remediation tab groups the open findings by artifact in fix order: the artifact with the highest weighted score first, with its severity mix and every finding with its remediation. Buttons open the artifact in the diagram view and, when the server or the Process Center connection defines a designer link template, in Process Designer.

Objects, diagrams and search

Objects & Diagrams lists every artifact of the application (and of the toolkits on request) grouped by type, services grouped by kind. Selecting one shows its findings, the service or process diagram from the Process Designer coordinates (flagged steps in red; click a step for its scripts, mappings and findings), variables, steps or flow objects with lanes and assignments, scripts, coach view options and resources, business object schema with nested types resolved, managed asset content, references and referenced-by lists, and the raw XML on request.

TWX Search searches text or regular expressions over names, scripts, conditions, mappings, documentation and raw XML, filtered by artifact type and toolkits.

Toolkit usage

Which toolkit artifacts does the application really use? Used: an application artifact references the toolkit artifact by id. Possible usage: an application script instantiates a business object by name that only this toolkit declares. No detected usage is not proof that the toolkit can be removed: runtime lookups by name and references from other toolkits still need a review. Duplicate snapshots of the same toolkit are merged; the report is exportable as HTML, PDF and CSV.

History and comparison

History lists the analyses of the workspace with health, findings and the trash button (permanent deletion of the uploaded file, the report and the metadata). Compare takes two analyses of the same application and reports added, removed and changed artifacts, toolkit version changes, and the findings that are new (regressions) or fixed; Hide accepted findings keeps the baseline out of the picture.

Settings and rule policies

The Settings page configures the current workspace:

  • Rule policy: which rule settings every analysis of the workspace uses. Built-in defaults (every rule with its default severity), Workspace settings (the rules edited on this page) or a central policy published by an administrator (Administration > Policies). Reports record the policy and its version.
  • Quality gate of the workspace (used with the built-in defaults or the workspace settings; a central policy carries its own gate).
  • Notifications (webhook, e-mail).
  • Rules: with Workspace settings selected, every rule can be disabled or given another severity and impact (1..3); the four severity weights and the thresholds of the size and complexity rules are editable; filter, bulk enable / disable / defaults, Export as a JSON file and Import (full or partial files, validated with warnings), Reset to defaults.

Saving the workspace re-evaluates the existing reports (accepted findings and verdict) so the History and the Dashboard stay consistent.

Quality gates and verdicts

A quality gate is a set of limits: health score at least N, Critical / Major / Minor / open findings at most N, weighted score at most N, and per-rule limits (for example TCA-JS-006=0: no hard-coded credentials). After each analysis every limit becomes a check with its actual value; the verdict is passed when every check passed, failed otherwise, and no gate when no limit is configured. Accepted findings are excluded before the checks run.

The verdict is shown in the report header and the dashboard, sent with notifications, printed in the executive PDF, and available to pipelines: GET api/report/<id>/verdict answers HTTP 200 (passed or no gate) or HTTP 422 (failed) with the checks.

Notifications

Per workspace (Settings): a webhook receives a JSON POST (event, application, snapshot, health, findings by severity, gate checks, policy, report link) and e-mail recipients receive a plain-text summary when the server has SMTP configured. Choose every completed analysis and / or only when the quality gate fails. Webhooks work with chat tools, ticketing systems and automation platforms that accept JSON.

Process Center and Business Automation Studio import

The Process Center page lists the process applications and snapshots of a Process Center and imports a snapshot directly: the server logs in, exports the snapshot exactly like the console does, queues the analysis and shows the report. The Process Center URL is an input on the page: type it with your user name and password, or pick a saved definition. Save this Process Center in my workspace keeps the URL, the user name and the password on the server for your workspace (or your team's), so the list opens with one click next time; saved definitions can be deleted at any time. Administrators can also share definitions with everyone (Administration > Process Center connections). Values typed on the page override a saved definition for the current request. Self-signed certificates are accepted after a first failed handshake. Toolkits are not listed; analyze them through the applications that bundle them.

Business Automation Studio (Cloud Pak for Business Automation, Workflow Authoring) is supported as a second repository type: choose it, enter the platform URL (the Cloud Pak / Zen address), the context root of Workflow Authoring (default /bas) and how to authenticate: Zen with user name and password or with user name and API key (the server obtains a platform token from /icp4d-api/v1/authorize), a bearer token you paste, or basic authentication where the gateway allows it. Listing and export then use the same repository API as a Process Center. This path was validated against a Studio simulator that mirrors the documented platform behaviour, not against a live Cloud Pak: if your Studio answers differently, the error message shows what it returned.

CI / CD integration and API

Every function of the application is an HTTP API described by an OpenAPI document (api/openapi.json) and browsable in the API page (Swagger UI) linked in the navigation bar. Authenticate with a personal access token (Account page): Authorization: Bearer <token>. Team workspace: header X-TCA-Workspace: team:<id>.

Pipeline recipe (shell):

BASE=https://analyzer.example.com; TOKEN=tca_...
# 1. queue the analysis (multipart upload)
JOB=$(curl -sf -H "Authorization: Bearer $TOKEN" -F file=@MyApp.twx "$BASE/api/analyze?async=1" | jq -r .id)
# 2. wait for the report
while :; do J=$(curl -sf -H "Authorization: Bearer $TOKEN" "$BASE/api/jobs/$JOB"); S=$(echo "$J" | jq -r .status)
  [ "$S" = done ] && break; [ "$S" = failed ] && { echo "$J"; exit 1; }; sleep 5; done
REPORT=$(echo "$J" | jq -r .reportId)
# 3. the verdict: HTTP 422 fails the build
curl -sf -H "Authorization: Bearer $TOKEN" "$BASE/api/report/$REPORT/verdict" || { echo "quality gate failed"; exit 1; }

One call for a Process Center snapshot (export, analysis and verdict; the client timeout must allow minutes for large exports):

curl -sf --max-time 1800 -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"url":"https://pc.example.com:9443","user":"ci-user","password":"...","app":"MYAPP","snapshot":"1.4.0"}' \
  "$BASE/api/enterprise/pc/evaluate" || { echo "quality gate failed"; exit 1; }
# a stored connection instead of URL and credentials: {"connection":"pc","app":"MYAPP","snapshot":"1.4.0"}
# the tip of a track instead of a named snapshot: {"connection":"pc","app":"MYAPP","track":"Main"}

Alternatives: POST api/analyze?gate=1 runs synchronously and answers 422 on a failed gate in one call; api/report/<id>/summary gives the numbers without the findings; api/report/<id>/pdf and executive.pdf attach reports to a build; api/enterprise/pc/import lets a pipeline analyze a snapshot straight from Process Center. Monitoring: api/health (liveness) and api/metrics (Prometheus).

Administration admin

  • Policies: create named rule policies (rules, severities, impacts, weights, thresholds, quality gate). Each save increments the version; reports record the policy and version. Workspaces select a policy in their Settings.
  • Teams: shared workspaces with members, team admins and an optional directory group (matched against the groups header of the single sign-on). Deleting a team can delete its workspace files.
  • Users (built-in accounts): list accounts with their storage, disable or enable, reset a password, delete an account with its workspace. Administrators are designated in the admins properties file on the server, not in the UI.
  • Process Center connections: stored connections with a read-only account and a designer link template (placeholders {branchId}, {snapshotId}, {projectId}, {objectId}).
  • Audit trail: analyses, deletions, settings and policy changes, accepted findings, sign-ups and logins, account and team administration; newest first, also written to the server log as JSON lines.
  • Server: health, the options in force and the metrics.

The rules

The Rules page lists every rule with its category, effective severity and impact, description, remediation and the reference it comes from (legacy code analyzer rules re-implemented for static analysis, IBM checkstyle and best-practice rules, JavaScript static analysis). Rules marked disabled or customized reflect the policy of the current workspace. Categories: Application, Dependencies, Services, Processes, Scripts, Syntax tree, Coaches, Business objects, Quality, Configuration and more.

Privacy, retention and deletion

  • Uploads are parsed on the server and stored with their report in the workspace of the uploader; nobody else sees them (personal) or only the team (team workspace). The analyzer makes no outbound connection of its own, except Process Center exports and notifications that you configure.
  • Delete (report header, History, Dashboard) removes the uploaded file, the report and the metadata immediately and permanently.
  • Signed-in users keep their data until they delete it, purge the workspace or delete the account. Anonymous demo workspaces are purged after the retention period shown on the Analyze page.
  • TWX exports contain source code and configuration: on a public server, only upload what you are allowed to store there.

Questions and answers

Why did the health score change without a new analysis? Accepting or reopening findings and changing the workspace policy re-evaluate the stored reports.

Why is a finding marked "review"? Its rule matches a pattern that is usually a problem but needs a look in context; filter with the confidence selector.

Can I move my rule settings to another installation? Yes: export the settings or the policy as JSON and import it there, or in the desktop app.

A report says the upload was discarded. The server keeps only reports (option keepUploads=false); analyze the export again if you need diagrams or search.

Where are the numbers in the health score from? score = severity weight (Critical 100, Major 40, Minor 10, Info 2, or the weights of the policy) × rule impact (1..3); health = 100 × e-density / 40 with density = total score / max(50, artifacts of the application).
